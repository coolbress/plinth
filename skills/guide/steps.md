# The guide's cells for each step

`scripts/guide-state.sh` reads this table beside the arsenal's "Where you
are, and what to do next" table (`skills/arsenal/SKILL.md`) and joins the two
by the first cell, which is the same text in both: the arsenal gives each
step's tool, its class, plinth's piece, the one alternative and what comes
next; this table gives what the guide says about the step. A step's row is in
both tables or in neither. Every command a How to use it cell names is a
command of the arsenal's table.

- Next action: what the step is for, the guide's gloss of its command.
- How to use it: when to use it and what to type.
- It leaves: what the step leaves behind.

## Steps

| Where you are | Next action | How to use it | It leaves |
| --- | --- | --- | --- |
| No repository yet (step 1) | Create it with its checks and rules; merge its first pull request on green | Type `/plinth:new-project <owner>/<name>` with the name the repository should have; it asks a few questions first | A repository on GitHub with its checks and rules, and its first pull request open |
| Repository made, its first pull request open (step 1) | Wait for green, squash and merge it, then bring `main` up to date in its folder | When every check on it is green, say `merge #N` with its number, or squash and merge it on its page | One commit on `main`, the project's first |
| A repository plinth did not make (step 1) | List what is missing; nothing is changed | Type `/plinth:floor-check` in the repository's folder | A list of what is missing, one fix each; nothing in the repository changes |
| First pull request merged (step 1) | Before step 2: a token that cannot change the checks; recommended next: the agent's own account, four things by hand | Nothing to type: open the token page and do what it says; the other two pages are recommended next, in that order | A token for the agent; recommended: an account for it, and four settings done by hand |
| An idea in your own words (step 2) | An interview, then an issue saying what "done" means | Type `/grilling` with the idea, before any code, and answer its questions one at a time | An issue that says what "done" means |
| A job bigger than one session (step 3) | A plan in one issue, cut into tickets | Type `/to-spec` to write the plan as one issue, then `/to-tickets #N` with that issue's number | A spec issue, and ticket issues cut from it that `/implement` takes one at a time |
| A ticket ready (step 4) | A fresh session, test first, one ticket | Type `/clear`, then `/implement #N` with the ticket's number: one ticket per session | A tested commit on a branch, from which the pull request is opened |
| A pull request with checks running (step 5) | Wait for green, then the three questions, and see it run | Wait for every check to be green, then ask the three questions of `${CLAUDE_PLUGIN_ROOT}/docs/how-to/run-a-project.md`, step 5: "What shows it works, and what did you not check?", "Can I see it?" (type `/run` to see the change working), "What did the reviewer say?" (read the review's findings in the description); before you merge, type `/security-review`: it reads the diff against `origin`'s default branch for injection, log-in and data-exposure risks, so the project needs an `origin` remote | The checks' results on the pull request, and the change seen running |
| Green, and seen working (step 6) | The person says "merge", for that pull request | Say `merge #N` with the pull request's number: the person says it, the agent never merges on its own | One squashed commit on `main`, and the pull request closed |
| Something broke (step 7) | When a merged change broke `main`: undo it first, then restore data it lost or changed, then reproduce and fix, then a short incident note; a leaked secret: revoke or rotate it first; otherwise reproduce, a failing test, then the fix | When a merge broke `main`, open the project's `docs/how-to/undo-a-merged-change.md` first; otherwise say `diagnose this: …` with what broke (a failing check, an error); type `/plinth:floor-check` when a plinth job fails on a plinth older than its latest release; type `/triage` on issues someone else opened; type `/doctor` when Claude Code, not the app, misbehaves | A revert pull request first when a merge broke `main`; a failing test that shows the bug, then the fix in a pull request; the incident note in the issue's Outcome; `/triage` leaves the issue labelled |
| Stopping, or coming back (step 8) | Put what is left in issues and pull requests; ask "where is this, what's next?" | Before you stop, leave what is left in issues and pull requests; coming back, type `/plinth:guide`; at a milestone's end or coming back, type `/plinth:records-check`; type `/handoff` before another tool or person takes over; on the same machine, type `/resume` to go back to an earlier conversation or `/recap` for a one-line summary, while on any machine the issues and pull requests stay the record | Issues and pull requests that say where the work is; `/handoff` a temporary file |
| Between pieces of work (step 9) | Dependency updates on green; the template update after a plinth release, or when the monthly reminder issue opens; a look back when `/plinth:guide` says one is due | Say `merge #N` for each Dependabot pull request on green, one at a time; type `/plinth:floor-check`, then `/plinth:template-update` when it or the monthly issue says the template is behind | Dependencies and the template brought up to date, each in a merged pull request; a look back: one dated issue and at most three tickets |
| A merged change to put out (release and deploy, after step 6) | A `web` app on Render goes out by itself once `main` is green; so does a `dashboard` on Render, and a `dashboard` on the person's computer is not put out; on a version tag the person pushes, `cli` and `library` publish to PyPI (a `Proprietary` one attaches its files to a GitHub release instead), `backend` its image to GHCR, `data-ml` its model as a GitHub release | Nothing to type for a `web` app or a `dashboard`; for the others, push a version tag as the project's `docs/how-to/publish-a-release.md` says | A new version: the app live, or a package, an image or a release for the tag |
| The project in use (operate) | Turn on the host's deploy-failure notification first; read the host's logs when something looks wrong; keep the spend limits and the restore you tried; what users report is written as an issue and sorted with `/triage` | Nothing to type: open the host's dashboard when something looks wrong | Nothing in the repository; what went wrong becomes an issue |
| Looking back on a piece of work (retrospective) | In the session you are looking back on, before you clear it, ask what to change for the next run; keep what you agree with as a rule or a check, written into an issue | Type `/retro` in the session you are looking back on, before `/clear`, and keep the suggestions you agree with; type `/insights` to see where recent sessions on this machine went wrong | Suggested rules and checks; the ones you keep go into an issue |
| Ending the project, or handing it over (end) | Do what the README says from step 2: data deleted or handed over, keys revoked, users told; what is left goes in issues | Nothing to type: follow the README from step 2; type `/handoff` when another person or tool takes it over | Data deleted or handed over, keys revoked, users told, and what is left in issues |
| A `web` project to put online (after step 1) | Choose where it runs: Render, built and checked by plinth, or another place that page names, whose steps and risks become the person's | Nothing to type: read the page and choose where it runs | The choice, made in the project |
| Correcting the agent the same way again (any step) | A line in `AGENTS.md`, then a reviewer rule, then a test that fails on the old mistake | Nothing to type: follow the page, the cheapest rung first | A line in `AGENTS.md`, a reviewer rule or a test, in a pull request |
| Unsure which skill now (any step) | Ask the person to type `/plinth:guide`: it is user-only, so the agent cannot call it | The person types `/plinth:guide` in the project's folder; this table is `/plinth:arsenal`, and on GitLab, where the guide does not read the project, it is the answer | Nothing: it only reads |
