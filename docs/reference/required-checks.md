# Required checks

## Ruleset rules

| Rule | Enforces on the default branch |
| --- | --- |
| `deletion` | The branch cannot be deleted |
| `non_fast_forward` | No force push |
| `pull_request` | Changes land through a pull request; squash is the only merge method; no approval is required; a new push dismisses an earlier approval |
| `required_status_checks` | Every check below reports a pass on the pull request's head, and the branch is up to date with the base (`strict`) |
| `code_scanning` | CodeQL has analysed the head and found no alert at `error` or at security severity `high` or above |
| Bypass list | Empty on this ruleset: its rules apply to owners too, `gh pr merge --admin` included. The second ruleset, `ruleset-merge.json` (`scripts/create-merge-ruleset.sh`), has one rule, `update`, and exempts the repository's admin role from it: only an admin merges into the default branch, and still only past the checks above |

## Required by `ruleset.json`

| Check | Asserts | A red means | The fix |
| --- | --- | --- | --- |
| `ci / pr-title` | The pull request title is Conventional Commits, `type: summary` or `type(scope): summary`, `!` before the colon for a breaking change; the type is one of the eleven standard types; the title does not end in `(#N)`, which the squash merge would repeat after adding its own number | The title does not match, or ends in `(#N)`; the job summary names the types and a table of common substitutes, or where the issue number goes instead | Edit the title. Where `ci.yml` lists the `edited` event, as plinth's own does, the check runs again on the edit; otherwise push a commit |
| `ci / lint` | `uv sync --locked` succeeds, `ruff check` and `ruff format --check` pass, and zizmor, given the job's token so its online audits run too, finds nothing at medium or above in `.github/workflows/` other than `known-vulnerable-actions` | The lockfile is missing or disagrees with `pyproject.toml`, ruff found a problem or an unformatted file, or zizmor found a workflow weakness, an impostor commit or ref confusion in a `uses:` pin among them. A published advisory for a pinned action (`known-vulnerable-actions`) never fails it: it is a `not yet confirmed` line, because the advisory database changes with no change in the repository | `uv lock`, `uv run ruff check --fix .`, `uv run ruff format .`; for zizmor, the rule it names in the log |
| `ci / typecheck` | `uv run mypy .` passes | A type error; the log names file and line | Fix the type at that line |
| `ci / test` | `uv run pytest` passes on `.python-version`, and on each version in the `extra-python-versions` input; with the `web` input `true`, against a disposable Postgres through `DATABASE_URL`. On `.python-version` pytest runs under coverage (`coverage run --branch --source=src`, or `--source=.` without a `src/` directory; coverage 7.10.7 installed into the synced environment with `uv pip install --require-hashes`, nothing added to `uv.lock`; a coverage the lock already carries is used as locked), and on a pull request the job summary says which of the changed lines ran, judged by diff-cover 9.7.1, installed in its own environment the same way, against the merge commit's first parent, test files left out; a changed Python file coverage's report does not have (outside `src/` when there is one, or omitted by the project's coverage configuration) is named, not passed. No outcome of that judgement fails the check yet (#503) | A failing test, or one that fails only on an extra version (the log's `python <version>` line says which) | `uv run pytest`; for an extra version, `uv run --isolated --python <version> --with pytest pytest -q`. A changed line no test runs is a `not yet confirmed` line, never a red: write a test that runs it. A line that only runs against a live service or as the process entry point carries `# pragma: no cover` with its reason, which `ci / diff-size` lists; a project-wide `[tool.coverage.report] exclude_also` is a `[tool.*]` change it lists too |
| `ci / build` | `uv build` makes a wheel and an sdist, each installs into a clean venv, and every package under `src/` imports | Packaging is broken: a wrong project name, missing package data or metadata, or an import that fails outside the checkout | Run `uv build` and install the file from `dist/` into a new venv |
| `ci / secrets` | gitleaks finds no secret in the repository's history, deleted files included | A commit on the branch carries a key, token or private key; it is already on GitHub | Revoke the secret where it was issued, then remove it from the branch's history |
| `ci / deps` | The pull request adds no dependency version with a known vulnerability at `deps-fail-on-severity` (default `high`) or above; not a pull request: a pass. On a private repository without GitHub Code Security, GitHub refuses the review (a bare 403); where the dependency graph still accepts an SBOM report request, the job then passes with a warning that nothing was checked, and where it does not (a disabled graph answers the same 403) the review runs and fails, and Dependabot alerts report a vulnerable dependency after the merge (#395) | A dependency the pull request adds or raises has such an advisory; the log names it | Move to a patched version, or drop the dependency |
| `ci / diff-size` | Added plus removed lines, docs and lockfiles excluded, are at most `max-diff-lines` (default 400); not a pull request: a pass. And a pull request that changes how strict the checks are (a `[tool.*]` table in `pyproject.toml`, a check configuration file, a test file deleted or moved out of the test paths, a kept Python test file that lost lines, an added skip or suppression marker in a Python file, the `archetype:` line of `.copier-answers.yml` changed, or the file deleted or moved, or the agent's own rules added, changed, deleted or moved: `AGENTS.md`, `CLAUDE.md` or `.claude/settings.json` at the repository root, or a file under `.claude/skills/` or `.claude/output-styles/`; with the `web` input also an added or changed line, not a comment, that names `public`, `login_not_required` or a name the head binds to one by an import's `as`, an assignment or a `getattr` (what marks a route public), any change to `notes/access.py`, an existing migration changed, deleted or renamed (an added one is not listed), `src/<package>/settings.py`, `render.yaml`, the `Dockerfile` or `tests/migration_rows.json`) carries an admin's approving review on its current head, where the head was pushed by an account that is not an admin of the repository or comes from a fork. The pusher is read from the branch's activity, not from the commit. A head an admin pushed, from a browser button too, or Dependabot (account id 49699333), needs no approval; any other bot's does. An approval is authorization, not a review. Needs `pull-requests: read` and `actions: write` granted to the caller's `ci` job: without them no job of the run starts | The change is too large to review in one pull request; the job summary gives the count. Or a change to the checks has no admin's approval on this head (an approval counts only for the commit it was given on), or what decides that could not be read | Split it into a stack of pull requests, each against the one below. For a change to the checks: if you agree with it, approve the pull request (Files changed, Review changes, Approve); where `ci.yml` lists the `pull_request_review` event the approval re-runs the latest red run, and where it does not, or cannot (a fork's pull request, whose token is read-only), the summary says to use "Re-run failed jobs" on the latest red `ci / diff-size`. A red because something could not be read: re-run the job. An edited workflow is never a red. A listed path the description does not name is a WARN in the log and the job summary: name the path in the description, then push. It does not see an assertion weakened with no line removed, an assertion dropped from a test the same pull request adds, a threshold passed as a `with:` input, a route opened through a function that wraps `public` and was there before, an `AGENTS.md` or `CLAUDE.md` below the root, other files under `.claude/` (`settings.local.json`, agents, commands), or a ruleset changed through the API, and does not judge whether a listed change lowers the standard |
| `ci / floor-check` | The repository still has the floor `/plinth:floor-check` reads: the document set, agent settings, the project files its archetype needs, a ruleset and CodeQL setup that still require these checks (on a private repository the CodeQL rule is expected only where GitHub Code Security is enabled, and this job, which does not read that, says in an INFO that `/plinth:floor-check`, run with a login that administers the repository, judges a missing rule), and a `ci` job on the default branch that calls plinth's `python-ci.yml` at a full commit SHA (for plinth itself, its own `./.github/workflows/plinth-ci.yml`). Here that item reads the pull request's own `ci.yml`: a pull request that keeps the call but weakens it fails, one that repairs it can merge, and one that removes the call removes this check too, which only a run from outside the pull request sees, after the merge. The same item reads two values of that job's `with:`: `max-diff-lines` of 0 or less or above 400 and `deps-fail-on-severity: critical` are each a WARN naming the value and plinth's default, which never changes the conclusion; an expression is a SKIP. Workflow files that call plinth at more than one commit (`ci.yml` and `label.yml` apart after a hand edit) are a WARN naming each file and its SHA, which never changes the conclusion either | At least one FAIL line in the job summary | Run `/plinth:floor-check`: each FAIL comes with one fix |

## What a job's summary says

| Form | Means |
| --- | --- |
| `pass: <standard>` | It applies here, ran, and held |
| `pass: <standard>, does not apply (<why>)` | It does not apply to this run |
| `fail: <standard>` | It applies here, ran, and did not hold |
| `not yet confirmed: <standard>, <why>; <what confirms it and when>` | It applies here but did not run or could not be read, including a step stopped by an earlier failed step in the job. Evidence about this commit that is missing: the same text is also a `::warning::` annotation, listed on the run's page and counted beside the workflow in the pull request's Checks tab, not shown in its merge box or Files changed. A step annotates at most nine lines, then one more saying how many are in the job summary: GitHub drops a step's annotations past ten with no notice. A line ending `; left to /plinth:floor-check` is a repository setting the Actions token never reads, the same in every run: it is in the summary and counted on the checker's summary line, not annotated |
| No line | The job was cancelled or timed out, or stopped before its checking step (checkout, a tool install, `ci / floor-check`'s fetch of the checker): the red or cancelled conclusion is the verdict |

| Check | Opens its summary with | Not yet confirmed on a run that otherwise passes | Passes with `does not apply` |
| --- | --- | --- | --- |
| `ci / pr-title` | The title's line | Never | Not a pull request |
| `ci / lint` | `uv sync --locked`, `ruff check`, `ruff format --check`, zizmor's audits except `known-vulnerable-actions`, and a pass for that one when no pinned action has a published advisory at medium or above | One line per published advisory for an action pinned here, naming the advisory, the action and its ref: zizmor's `known-vulnerable-actions`, reported and never failing the job. A pin raised past the advisory's fixed version confirms it | Never |
| `ci / typecheck` | `uv sync --locked`, mypy | Never | Never |
| `ci / test` | `uv sync --locked`, pytest on `.python-version`, pytest on the extra versions, the changed lines under the tests | The changed lines, reported and never failing the job: none of the N changed executable lines ran; N of M did not run (each names up to nine files with their lines, and the step's log has the rest); coverage recorded no line in the whole project, usually pytest-cov's `--cov` in the project's `addopts` owning the tracer; a changed Python file is not in coverage's report, named with the others; pytest or the coverage install did not succeed; diff-cover, git's list of changed files or the judging step did not finish. A test that runs the lines, or `# pragma: no cover` with its reason, confirms it | The extra versions, when `extra-python-versions` is empty. The changed lines, when it is not a pull request or no changed line is executable (a comment, a string inside a call, a test file) |
| `ci / build` | `uv sync --locked`, `uv build`, the install smoke | Never | Never |
| `ci / secrets` | gitleaks | Never | Never |
| `ci / deps` | The dependency review's line, after the review action's own summary on a pull request: a job's summary is its steps' summaries in step order | A private repository without GitHub Code Security, where GitHub refuses the review (#395); Dependabot alerts report a vulnerable dependency after the merge. A head Dependabot pushed: CodeQL does not analyse it, and `main` is analysed after the merge (#179) | Not a pull request |
| `ci / diff-size` | The count against `max-diff-lines`, then, when the pull request changes how strict the checks are, the approval's line | A change to the checks on a head an admin or Dependabot pushed: no approval is asked, and the line says the change is the person's decision; reading the table above it before merging confirms it | Not a pull request. `max-diff-lines: 0` passes as measured and not enforced, with the count |
| `ci / floor-check` | A pass line, or one fail line per FAIL, then the checker's report | Each SKIP line, annotated. Each read the Actions token cannot make and `/plinth:floor-check` with a login that administers the repository does, ending `; left to /plinth:floor-check` and not annotated: push protection, the bypass actors of both rulesets, the CodeQL default setup languages, the squash commit settings, and a private repository's missing CodeQL rule | Never |
| `ci / code-growth` (not required) | One line, code size within the conventions, then a table of what is above them | Something above a convention: the line is in the summary and not annotated, and up to three warnings name the largest functions and files, each with the next step; reported and never failing the job. `uv sync --locked`, ruff or git's list of files did not finish: one annotated line. A clean-up that brings them under confirms it | No Python file under `src/`, or the project without one |

| Check | Asserts | A red means | The fix |

| `image` | The container image builds, runs, and its first log line carries `"message": "started"`; required for `backend`, `data-ml` and `web` | The image does not build, does not start, or does not log that it started | `docker build -t app . && docker run --rm app` locally |

## Required for the web archetype

| Check | Asserts | A red means | The fix |
| --- | --- | --- | --- |
| `ci / migrations` | With the `web` input `true`, against a disposable Postgres: `makemigrations --check`, naming every app that has models, finds no model change without its migration, so an app whose migrations package was moved or deleted fails too; `migrate` applies to an empty database; and the rows in `tests/migration_rows.json`, read from the base commit and loaded under the base's migrations, keep their counts after this head's migrations: every table of a model the file holds rows for, and their many-to-many tables. The file may not hold `contenttypes.ContentType`, `auth.Permission` or `sessions.Session`. A base without the file is a `not yet confirmed` line, never a pass. With `web` `false`: a pass, does not apply | A model change has no migration, a migration does not apply from empty, or a table lost or gained rows; the job summary names the table and both counts | `uv run python manage.py makemigrations`, then run `migrate` on an empty database. A row-deleting migration on purpose: change `tests/migration_rows.json` in the same pull request, which `ci / diff-size` puts to a person, and the next pull request's base carries it |
| `ci / deploy-check` | With the `web` input `true`: `manage.py check --deploy --fail-level WARNING` passes with production-shaped settings (debug off, a key made for the run, placeholder hosts and database URL). With `web` `false`: a pass, does not apply | A deployment warning: debug on, no allowed hosts, a weak key, a missing HTTPS or cookie setting; the deploy step's log names each | Fix the setting the warning names; HSTS preload and subdomains are the owner's choice and are rendered silenced, with the reason |

## Code scanning rule

| Check | Asserts | A red means | The fix |
| --- | --- | --- | --- |
| `CodeQL` | CodeQL analysed the head with no alert at the thresholds above. On a private repository the rule is there only where GitHub Code Security is enabled ([about private repositories](../explanation/concepts.md#about-private-repositories)) | An alert, or no analysis: default setup is off, or the first push of a new repository was not analysed | Fix the alert the check links to; with no analysis, turn default setup on or push the recovery commit `/plinth:new-project` prints |
| `CodeQL` | On a head Dependabot pushed, nothing: default setup starts no analysis, the check lands `neutral` and the rule passes | Not applicable | `ci / deps` and the tests still run on that head, and `main` is analysed after the merge |

## Secrets at the push

| Setting | Does | Needs | Where plinth stands |
| --- | --- | --- | --- |
| Push protection | GitHub refuses a push that carries a secret in a format it knows. The person pushing can still let it through, and a secret in a format it does not block by default passes; `ci / secrets` reports those after the push | Free on a public repository; on a private one, GitHub Secret Protection | `/plinth:new-project` turns it on. `/plinth:floor-check` reports it on, off (a WARN with the call that turns it on, never a red), or not verified when the token does not read the repository's security settings or GitHub reports no status. On a private repository where secret scanning is disabled it is an INFO naming the gap, not a WARN. `ci / floor-check` runs on the Actions token, which does not read them, and says so in an INFO: the skill, with a person's login, is the run that reads it. It is a setting, not a required check |
| Ruleset rule "require secret scanning alerts are resolved" | Blocks the merge of a pull request while an alert is open for a secret its commits introduced | GitHub Secret Protection or GitHub Advanced Security, both paid; in [public preview since 2026-09-09](https://github.blog/changelog/2026-09-09-block-pull-requests-with-exposed-secrets-from-merging/) | plinth does not set it and does not read it. With the licence, add it to the ruleset in the repository's settings |

## On GitLab

| Item | On a project made with `--host gitlab` |
| --- | --- |
| Job names | `lint`, `typecheck`, `test`, `build`, `secrets`, `deps`, `diff-size`, `pr-title` and `floor-check`, from [plinth's GitLab pipeline](gitlab-ci.md); a backend or data-ml project adds `docker-image`, the job GitHub calls `image` |
| Required by name | No: "Pipelines must succeed" takes the pipeline as a whole, so a merge request that drops a job still merges when what is left passes ([about GitLab](../explanation/concepts.md#about-gitlab)) |
| After the merge | `/plinth:floor-check` reads whether the default branch still includes the pipeline at a full commit SHA |
| Not on GitLab Free | A ruleset, the `code_scanning` rule, push protection, a required approval. `diff-size` lists a change to the checks and never asks for an approval: a merge request could drop the job, and Free approvals do not block a merge |
| A change to the agent's own rules | `AGENTS.md`, `CLAUDE.md` or `.claude/settings.json` at the root, or a file under `.claude/skills/` or `.claude/output-styles/`, added, changed, deleted or moved, is listed by `diff-size` on both hosts, with the same reasons. On GitHub, `ci / diff-size` asks for an admin's approving review on the head when an account that is not an admin pushed it, or the head comes from a fork. On GitLab it is a WARN in the log when the merge request's description does not name the path, and the job still passes: nothing asks for an approval |

## Optional

| Check | Asserts | A red means | The fix |
| --- | --- | --- | --- |
| `ci / code-growth` | Not required: no ruleset requires it, and it never fails. It measures with the project's locked ruff and git's file list, under `src/` or the whole project without one: functions above complexity 10 (`C901`) or 50 statements (`PLR0915`), and Python files above 1000 lines. These limits are conventions, each the default of the tool it comes from, not validated numbers; ruff runs with `--isolated --ignore-noqa`, so the project's own limits, `# noqa` comments, per-file ignores and excludes do not change what it measures. Whether it is ever required is decided after projects have shown its warnings (#705) | Never red from what it measures; a red is a checkout or the uv install failing | Above a convention: run `/improve-codebase-architecture` on the file the warning names, or `/ponytail-audit` for the whole project |
| `third-party / review` | An accepted reviewer reviewed the pull request's current commit; required only once added to the ruleset, as plinth's own `main` has it | No review arrived on the current commit within the wait | [Configure the third-party reviewer](../how-to/configure-the-third-party-reviewer.md) |
