# Required checks

## Ruleset rules

| Rule | Enforces on the default branch |
| --- | --- |
| `deletion` | The branch cannot be deleted |
| `non_fast_forward` | No force push |
| `pull_request` | Changes land through a pull request; squash is the only merge method; no approval is required; a new push dismisses an earlier approval |
| `required_status_checks` | Every check below reports a pass on the pull request's head, and the branch is up to date with the base (`strict`) |
| `code_scanning` | CodeQL has analysed the head and found no alert at `error` or at security severity `high` or above |
| Bypass list | Empty on this ruleset: its rules apply to owners too, `gh pr merge --admin` included. The second ruleset, `ruleset-merge.json` (`scripts/create-merge-ruleset.sh`), has one rule, `update`, and exempts the repository's admin role from it: only an admin merges into the default branch, and still only past the checks above |

## Required by `ruleset.json`

| Check | Asserts | A red means | The fix |
| --- | --- | --- | --- |
| `ci / pr-title` | The pull request title is Conventional Commits, `type: summary` or `type(scope): summary`, `!` before the colon for a breaking change; the type is one of the eleven standard types; the title does not end in `(#N)`, which the squash merge would repeat after adding its own number. `Revert "<title>"`, the title GitHub's Revert button and `gh pr revert` write, passes when `<title>` passes on its own, nested reverts included. Then the description: every issue GitHub says the merge will close is named on the description's closing line (`Closes #N` in a paragraph of its own, directly above the attribution), since a closing keyword before `#N` closes that issue in a sentence too | The title does not match, or ends in `(#N)`; the job summary names the types and a table of common substitutes, or where the issue number goes instead. A refused `Revert "…"` title names the form that passes. Or the merge would close an issue the closing line does not name, or GitHub's list could not be read; the log and the summary quote the line to reword | Edit the title, or reword the sentence so the keyword does not stand before the number (`Part of #N` when the pull request does not complete the issue). Where `ci.yml` lists the `edited` event, as plinth's own and the template's do, the check runs again on the edit; otherwise push a commit |
| `ci / lint` | `uv sync --locked` succeeds, `ruff check` and `ruff format --check` pass, and zizmor, given the job's token so its online audits run too, finds nothing at medium or above in `.github/workflows/` other than `known-vulnerable-actions` | The lockfile is missing or disagrees with `pyproject.toml`, ruff found a problem or an unformatted file, or zizmor found a workflow weakness, an impostor commit or ref confusion in a `uses:` pin among them. A published advisory for a pinned action (`known-vulnerable-actions`) never fails it: it is a `not yet confirmed` line, because the advisory database changes with no change in the repository | `uv lock`, `uv run ruff check --fix .`, `uv run ruff format .`; for zizmor, the rule it names in the log |
| `ci / typecheck` | `uv run mypy .` passes | A type error; the log names file and line | Fix the type at that line |
| `ci / test` | `uv run pytest` passes on `.python-version`, and on each version in the `extra-python-versions` input; with the `web` input `true`, against a disposable Postgres through `DATABASE_URL`. On a pull request, pytest on `.python-version` runs under coverage (on the source the project's coverage configuration names, `source`, `source_pkgs` or `source_dirs` in `pyproject.toml`, `.coveragerc`, `setup.cfg` or `tox.ini`, when it names one; otherwise `coverage run --branch --source=src`, or `--source=.` without a `src/` directory; coverage 7.10.7 installed into the synced environment with `uv pip install --require-hashes`, nothing added to `uv.lock`; a coverage the lock already carries is used as locked), and on a pull request the job summary says which of the changed lines ran, judged by diff-cover 9.7.1, installed in its own environment the same way, against the merge commit's first parent, test files left out; a changed Python file coverage's report does not have (outside the measured source, or omitted by the project's coverage configuration) is named, not passed. No outcome of that judgement fails the check yet (#503). On a push nothing reads coverage's data, so pytest runs without it (#941). The job's time limit is the `test-timeout-minutes` input, whole minutes from 1 to 360, default 10; pytest and each extra version run under coreutils `timeout` with what is left of it less 120 seconds (`TEST_MARGIN_SECONDS`), or a fifth of the limit when that is shorter, kept for the changed lines and the summary, so a run that reaches it still ends with a summary that says the limit stopped it. A project gets the input by raising both `coolbress/plinth` `uses:` lines, in `ci.yml` and `label.yml`, to the release that carries it, and sets it under the `ci` job's `with:` (`test-timeout-minutes: 20`) | A failing test, or one that fails only on an extra version (the log's `python <version>` line says which). Or pytest stopped at the time limit, not at a failing test: the summary's line says so with the minutes and the input's name. Or `test-timeout-minutes` is not whole minutes from 1 to 360 | `uv run pytest`; for the time limit, measure first: `uv run pytest --durations=20` lists the slowest tests, and when a few take most of the time, make them faster; raise `test-timeout-minutes` under the `ci` job's `with:` in `ci.yml` when none stands out and the time moves between runs of the same commit, which comes from the runner (the same suite measured 345 s and 589 s one commit apart, #941); for an extra version, `uv run --isolated --python <version> --with pytest pytest -q`. A changed line no test runs is a `not yet confirmed` line, never a red: write a test that runs it. A changed file outside `src/` that is not in coverage's report: name its directory in the project's coverage `source` (`[tool.coverage.run] source` in `pyproject.toml`, say), which `ci / test` then measures. A line that only runs against a live service or as the process entry point carries `# pragma: no cover` with its reason, which `ci / diff-size` lists; a project-wide `[tool.coverage.report] exclude_also` is a `[tool.*]` change it lists too |
| `ci / build` | `uv build` makes a wheel and an sdist, each installs into a clean venv, and every package under `src/` imports. In a uv workspace (`[tool.uv.workspace]` in the root `pyproject.toml`) it runs `uv build --all-packages`, installs only the root package's wheel and sdist, each with `--find-links dist` and every built member pinned to its version in `dist/`, so a same-named package on the index is not taken instead, and imports the `src/` packages of the root and of each member the root installed; a member uv does not package (no `[build-system]`, or `tool.uv.package = false`) is neither built nor imported, and a packaged member the root does not depend on is named in the log, not imported. A root uv does not package is not built, and the check fails saying so; its sdist did not install before either | Packaging is broken: a wrong project name, missing package data or metadata, or an import that fails outside the checkout | Run `uv build` (`uv build --all-packages` in a workspace) and install the root's file from `dist/` into a new venv (with `--find-links dist` in a workspace) |
| `ci / secrets` | gitleaks finds no secret in the repository's history, deleted files included | A commit on the branch carries a key, token or private key; it is already on GitHub | Revoke the secret where it was issued, then remove it from the branch's history |
| `ci / deps` | The pull request adds no dependency version with a known vulnerability at `deps-fail-on-severity` (default `high`) or above; not a pull request: a pass. On a private repository without GitHub Code Security, GitHub refuses the review (a bare 403); where the dependency graph still accepts an SBOM report request, osv-scanner (2.6.0, checked against its SHA-256, the same as GitLab's `deps`) compares `uv.lock` at the pull request's head with `uv.lock` at its merge base against one offline copy of the OSV database instead, and only an advisory the head has and the base does not counts; its pass line ends `(osv-scanner, the OSV database)`, and a scan that cannot run fails (#1073). Where the graph does not accept it (a disabled graph answers the same 403) the review runs and fails (#395) | A dependency the pull request adds or raises has such an advisory; the log names it. Where osv-scanner compared them, the job also fails when it could not run: the download, its checksum, or a lockfile it could not read, the error above the verdict | Move to a patched version, or drop the dependency |
| `ci / diff-size` | Added plus removed lines, docs and lockfiles excluded, are at most `max-diff-lines` (default 400); not a pull request: a pass. In a pull request whose `.copier-answers.yml` changes `archetype:` and keeps `_commit:` (an archetype move at the tag it records, as `/plinth:template-update --archetype` makes it), `.github/workflows/release.yml` is left out of that count and named with its lines on the count's line and in the summary: the template renders it whole for each archetype, and between one that publishes to PyPI and one that publishes an image either half of a split inside it is 442 lines or more (#1044). The `archetype:` change is a change to the checks below, so it is put to an admin like any other; GitLab's `diff-size` counts the file. And a pull request that changes how strict the checks are (a `[tool.*]` table in `pyproject.toml`, a check configuration file, a test file deleted or moved out of the test paths, a kept Python test file that lost lines, an added skip or suppression marker in a Python file, the `archetype:` line of `.copier-answers.yml` changed, or the file deleted or moved, or the agent's own rules added, changed, deleted or moved: `AGENTS.md`, `CLAUDE.md` or `.claude/settings.json` at the repository root, or a file under `.claude/skills/` or `.claude/output-styles/`; with the `web` input also an added or changed line, not a comment, that names `public`, `login_not_required` or a name the head binds to one by an import's `as`, an assignment or a `getattr` (what marks a route public), any change to `notes/access.py`, an existing migration changed, deleted or renamed (an added one is not listed), `src/<package>/settings.py`, `render.yaml`, the `Dockerfile` or `tests/migration_rows.json`) carries an admin's approving review on its current head, where the head was pushed by an account that is not an admin of the repository or comes from a fork. The pusher is read from the branch's activity, not from the commit. A head an admin pushed, from a browser button too, or Dependabot (account id 49699333), needs no approval; any other bot's does. An approval is authorization, not a review. Needs `pull-requests: read` and `actions: write` granted to the caller's `ci` job: without them no job of the run starts. And no line the pull request adds, in any tracked file and not only under `working-directory`, is a merge conflict marker: `<<<<<<<`, `\|\|\|\|\|\|\|` or `>>>>>>>` at the start of a line, alone or followed by a space and a label, or `=======` alone on its line where the same file's added lines carry one of the other three, since alone it is also a Markdown heading's underline (#936). A marker the base already has passes; one inside a fenced code block a document adds fails, and an indented one or one in a code span passes. Not a pull request: a pass | The change is too large to review in one pull request; the job summary gives the count. Or a line the pull request adds is a conflict marker; the log names each file and line, the first nine also as annotations. Or a change to the checks has no admin's approval on this head (an approval counts only for the commit it was given on), or what decides that could not be read | Split it along its dependency chain into pull requests that land one after another, each branched from `main` after the one before it merged: under squash merges, a pull request against another one conflicts once the lower one changes. For a change to the checks: if you agree with it, approve the pull request (Files changed, Review changes, Approve); where `ci.yml` lists the `pull_request_review` event the approval re-runs the latest red run, and where it does not, or cannot (a fork's pull request, whose token is read-only), the summary says to use "Re-run failed jobs" on the latest red `ci / diff-size`. A red because something could not be read: re-run the job. An edited workflow is never a red. A listed path the description does not name is a WARN in the log and the job summary: name the path in the description, then push. It does not see an assertion weakened with no line removed, an assertion dropped from a test the same pull request adds, a threshold passed as a `with:` input, a route opened through a function that wraps `public` and was there before, an `AGENTS.md` or `CLAUDE.md` below the root, other files under `.claude/` (`settings.local.json`, agents, commands), or a ruleset changed through the API, and does not judge whether a listed change lowers the standard. A conflict marker: resolve the conflict, delete the marker lines and push |
| `ci / floor-check` | The repository still has the floor `/plinth:floor-check` reads: the document set, agent settings, the project files its archetype needs, a ruleset and CodeQL setup that still require these checks (on a private repository the CodeQL rule is expected only where GitHub Code Security is enabled, and this job, which does not read that, says in an INFO that `/plinth:floor-check`, run with a login that administers the repository, judges a missing rule), and a `ci` job on the default branch that calls plinth's `python-ci.yml` at a full commit SHA (for plinth itself, its own `./.github/workflows/plinth-ci.yml`). Here that item reads the pull request's own `ci.yml`: a pull request that keeps the call but weakens it fails, one that repairs it can merge, and one that removes the call removes this check too, which only a run from outside the pull request sees, after the merge. The same item reads two values of that job's `with:`: `max-diff-lines` of 0 or less or above 400 and `deps-fail-on-severity: critical` are each a WARN naming the value and plinth's default, which never changes the conclusion; an expression is a SKIP. Workflow files that call plinth at more than one commit (`ci.yml` and `label.yml` apart after a hand edit) are a WARN naming each file and its SHA, which never changes the conclusion either | At least one FAIL line in the job summary | Run `/plinth:floor-check`: each FAIL comes with one fix |

## What a job's summary says

| Form | Means |
| --- | --- |
| `pass: <standard>` | It applies here, ran, and held |
| `pass: <standard>, does not apply (<why>)` | It does not apply to this run |
| `fail: <standard>` | It applies here, ran, and did not hold |
| `not yet confirmed: <standard>. Why: <reason>. What confirms it: <run>.` | It applies here but did not run or could not be read, including a step stopped by an earlier failed step in the job. One fact per sentence: what is not confirmed, why, and the run that confirms it. `ci / test`, `ci / lint`, `ci / typecheck`, `ci / build`, `ci / secrets`, `ci / deps`, `ci / migrations`, `ci / deploy-check`, `ci / pr-title`, `ci / diff-size`, `ci / code-growth` and `ci / web-audit` say it in this form, and so does every job's shared line for a step stopped by an earlier one. Still in the older form, `not yet confirmed: <standard>, <why>; <what confirms it>`: the floor checker's own lines (`ci / floor-check`), and GitLab's until #1101, except the `test` job's and the merge request description's, which share their code with GitHub's and follow it. Evidence about this commit that is missing: the same text is also a `::warning::` annotation, listed on the run's page and counted beside the workflow in the pull request's Checks tab, not shown in its merge box. A step that did not run because an earlier step failed is in the summary only once the job has a `fail:` line: the failure already says it, and a warning beside it would read like the cause or Files changed. A step annotates at most nine lines, then one more saying how many are in the job summary: GitHub drops a step's annotations past ten with no notice. A line ending `; left to /plinth:floor-check` is a repository setting the Actions token never reads, the same in every run: it is in the summary and counted on the checker's summary line, not annotated |
| No line | The job was cancelled or timed out, or stopped before its checking step (checkout, a tool install, `ci / floor-check`'s fetch of the checker): the red or cancelled conclusion is the verdict |

| Check | Opens its summary with | Not yet confirmed on a run that otherwise passes | Passes with `does not apply` |
| --- | --- | --- | --- |
| `ci / pr-title` | The title's line, then the description's, above the list of what the merge closes | One line for each of two fields the description leaves missing, empty or bare: a `What I checked myself` section saying what the person ran, opened or read and what they saw, or `Skipped: <reason>` ("done" or `Skipped:` alone counts as empty), and a `Review:` line naming `fresh-context`, `third-party (<name>)`, `same-session (not independent)` or `none (<reason>)` (#810). And one line for each bare `#N` in the description above the repository's highest issue or pull request number (they share one count), naming it and the `owner/repo#N` form a reference to another repository's is written in; a reference with a path before it, one inside a code span, a fenced block, an HTML comment or a link, and a number the repository has are never named (#826). That highest number is read with the job's token; when it cannot be read, the log says why and no number is named. A discussion's number, which shares the count but is not read, can be named. Filling the field, rewriting the reference, and the next run confirm it; none ever fails the job. On a pull request a bot wrote (GitHub's `user.type` Bot: Dependabot's, and any GitHub App's or Actions workflow's, an AI agent's under an app account included) the two fields give one `pass:` line saying they do not apply; the closing comparison and the bare `#N` lines still run (#1141) | Not a pull request: one line for the title and the description, and plinth's description check is not fetched (#1141) |
| `ci / lint` | `uv sync --locked`, `ruff check`, `ruff format --check`, zizmor's audits except `known-vulnerable-actions`, and a pass for that one when no pinned action has a published advisory at medium or above | One line per published advisory for an action pinned here, naming the advisory, the action and its ref: zizmor's `known-vulnerable-actions`, reported and never failing the job. A pin raised past the advisory's fixed version confirms it | Never |
| `ci / typecheck` | `uv sync --locked`, mypy | Never | Never |
| `ci / test` | `test-timeout-minutes` when it is not whole minutes from 1 to 360 (a `fail:` line), `uv sync --locked`, pytest on `.python-version`, pytest on the extra versions (each a `fail:` line saying the time limit stopped it when it did, with the minutes, the input's name and `uv run pytest --durations=20` to run before raising it), the changed lines under the tests | The changed lines, reported and never failing the job: none of the N changed executable lines ran; N of M did not run (each names up to nine files with their lines, and the step's log has the rest); coverage recorded no line in the whole project, usually pytest-cov's `--cov` in the project's `addopts` owning the tracer; a changed Python file is not in coverage's report, named with the others; pytest or the coverage install did not succeed; diff-cover, git's list of changed files or the judging step did not finish. A test that runs the lines, or `# pragma: no cover` with its reason, confirms it | The extra versions, when `extra-python-versions` is empty. The changed lines, when it is not a pull request or no changed line is executable (a comment, a string inside a call, a test file) |
| `ci / build` | `uv sync --locked`, `uv build`, the install smoke | Never | Never |
| `ci / secrets` | gitleaks | Never | Never |
| `ci / deps` | The dependency review's line, after the review action's own summary on a pull request: a job's summary is its steps' summaries in step order; where GitHub refuses the review, osv-scanner's line (#1073) | Where GitHub refuses the review and osv-scanner did not run because an earlier step failed. A head Dependabot pushed: CodeQL does not analyse it, and `main` is analysed after the merge (#179) | Not a pull request |
| `ci / diff-size` | The count against `max-diff-lines`, the conflict-marker line, then, when the pull request changes how strict the checks are, the approval's line | A change to the checks on a head an admin or Dependabot pushed: no approval is asked, and the line says the change is the person's decision; reading the table above it before merging confirms it | Not a pull request. `max-diff-lines: 0` passes as measured and not enforced, with the count |
| `ci / floor-check` | A pass line, or one fail line per FAIL, then the checker's report; each FAIL and WARN there ends in one next action and a link. Any FAIL also gives one annotation, titled `ci / floor-check`, however many there are: the first and the count, and the next step, within 300 characters; the log ends with `failed:`, `next:` and `more:` | Each SKIP line, annotated. Each read the Actions token cannot make and `/plinth:floor-check` with a login that administers the repository does, ending `; left to /plinth:floor-check` and not annotated: push protection, private vulnerability reporting, the Actions allowlist, the Actions token settings, the bypass actors of both rulesets, the CodeQL default setup languages, the squash commit settings, and a private repository's missing CodeQL rule | Never |
| `ci / code-growth` (not required) | One line, code size within the conventions, then a table of what is above them | Something above a convention: the line is in the summary and not annotated, and up to three warnings name the largest functions and files, each one sentence with the next step; reported and never failing the job. `uv sync --locked`, ruff or git's list of files did not finish: one annotated line. A Python file on git's list that ruff did not measure (it skipped it, could not read it or could not parse it): an annotated line naming it and why, the first of the three warnings. A clean-up that brings them under confirms it | No Python file under `src/`, or the project without one |
| `ci / web-audit` (not required) | One line per page and tool: Lighthouse's four scores for `/` (logged in) and the log-in page (not logged in), and whether axe-core's automated rules found a violation there; then a table of the scores, a table per page of what axe-core found, and the sentence that automated checks catch only part of accessibility | A violation axe-core found: one annotated line per page naming each rule, its impact and how many elements; reported and never failing the job. The app image did not build or start, the migrations did not apply, Node, Chrome for Testing or the tools did not install, or the audit did not finish: one annotated line with the reason. A page Lighthouse could not load, an error status, a person the audit could not log in, or a session that sent `/` back to the log-in page: an annotated line saying so. Fixing the page, or a run that gets past the step, confirms it | The `web` input `false` |

## When a check fails

| Where | What a failing check in this shape says there |
| --- | --- |
| The last lines of the job's log (`gh run view --job <id> --log`; `--log-failed` shows only the step that failed, not the Verdict that prints these lines) | `failed: <what failed>`, `next: <one action>`, `more: <a link to its section below>`, the last thing plinth prints in the job. Above them the Verdict step prints its summary lines |
| An annotation on the pull request | One, titled with the check's name, `ci / <job>`: what failed and the next step, in at most 300 characters |
| The job's summary | It opens with the `fail:` line, as in [What a job's summary says](#what-a-jobs-summary-says) |
| The job's conclusion | Unchanged: the Verdict step exits 0, so the red and GitHub's own "Process completed with exit code 1" come from the step that failed |
| The link | At the plinth commit the project's `ci.yml` calls (`job.workflow_sha`), so the page it opens is the one that commit shipped. The headings below are the check names, which change only in a MAJOR release |

### ci / pr-title

| What failed | The next step |
| --- | --- |
| `PR title is not Conventional Commits: <title>` | Rewrite it as `type(scope): summary`, the type one of `feat` `fix` `docs` `style` `refactor` `perf` `test` `build` `ci` `chore` `revert`; a revert as `Revert "type(scope): summary"` |
| `PR title ends in a number: <title>` | Remove the trailing `(#N)` and name the issue on the description's closing line ([CONTRIBUTING.md](../../CONTRIBUTING.md#land-a-change)) |
| `#<N>'s description: <the first FAIL>` | The description would close an issue outside its closing line: reword the sentence so the keyword does not stand before the number, or put it on the closing line. The step's one annotation says it; `closing-references.sh` prints none of its own there |
| `PR description, plinth's check could not be fetched` | Re-run the job |

### ci / lint

| What failed | The next step |
| --- | --- |
| `ruff check: <N> findings, the first <code> at <file>:<line>` | Run `uv run ruff check .` here, fix what it names, and push. Each finding is also an annotation at its file and line, with its code, nine at most in the job, then a line saying how many there are; ruff's whole output is in the ruff check step's log |
| `ruff format --check: <N> files not formatted: <files>` | Run `uv run ruff format` here, commit what it changes, and push. Each file is also an annotation, within the same nine |
| `ruff check could not run` or `ruff format --check could not run` | ruff stopped with its own error and named no file and line (exit 2: a setting it cannot read, an unknown rule, ruff missing from the dev dependencies), not a finding: run the same command here and fix what stops it; its error is in that step's log |
| `uv sync --locked` | Run `uv sync --locked` here; when it says `uv.lock` needs updating, run `uv lock`, commit `uv.lock` and push |
| `zizmor's audits` | Run `uvx zizmor@1.29.0 --min-severity medium .github/workflows/` here, fix what it names, and push |

### ci / typecheck

| What failed | The next step |
| --- | --- |
| `mypy: <N> errors, the first at <file>:<line> [<code>]` | Run `uv run mypy .` here, fix what it names, and push. Each error is also an annotation at its file and line, with its code, nine at most, then a line saying how many there are; mypy's whole output is in the mypy step's log |
| `mypy could not run` | mypy stopped with its own error and named no file and line (exit 2: a setting it cannot read, a path that does not exist, mypy missing from the dev dependencies), not an error in the code (a syntax error also exits 2; it names its file and line, so it is reported as an error there): run `uv run mypy .` here and fix what stops it; its error is in the mypy step's log |
| `uv sync --locked` | As for `ci / lint` |

### ci / test

| What failed | The next step |
| --- | --- |
| `pytest on .python-version: <test> failed` | Run `uv run pytest <test>` here, fix what it shows, and push. Each failed test is also an annotation at its file and line, nine at most, then a line saying how many there are; pytest's whole output is in the pytest step's log |
| `pytest on python <version>: <test> failed` | The same test on one of the `extra-python-versions`: run `uv run --isolated --python <version> --with pytest pytest <test>` here |
| `pytest on .python-version` alone | pytest failed and its log has no `FAILED` or `ERROR` line, for example a crash before any test ran: read the pytest step's log above its last line, fix what it names, and push |
| `stopped at the time limit` | The job's limit stopped pytest, not a failing test: run `uv run pytest --durations=20` here and make the slowest tests faster; raise `test-timeout-minutes` only when none stands out |
| `uv sync --locked` | Run `uv sync --locked` here; when it says `uv.lock` needs updating, run `uv lock`, commit `uv.lock` and push |
| `a disposable Postgres for the tests` | With the `web` input `true`, the Postgres container did not start: re-run the job; the Start Postgres step's log says why |
| `test-timeout-minutes` | The input is not whole minutes from 1 to 360: set it under `ci.yml`'s `with:` |

### ci / build

| What failed | The next step |
| --- | --- |
| `uv build` | Run `uv build` here, fix what it names, and push |
| `install smoke, import <module> from <artifact> failed in a clean venv` | Run `uv build` here, then `uv run --isolated --no-project --with <artifact> python -c 'import <module>'`, and add the module or the dependency it is missing |
| `install smoke, <artifact> did not install in a clean venv` | Run `uv build` here, then install that artifact into a new venv with `uv pip install`, fix what it names, and push |
| `install smoke, uv build made no wheel or sdist of the root package` | A workspace whose root is not a package: add a `[build-system]` table to `pyproject.toml`, or set `tool.uv.package = true` |
| `uv sync --locked` | Run `uv sync --locked` here; when it says `uv.lock` needs updating, run `uv lock`, commit `uv.lock` and push |

### ci / secrets
